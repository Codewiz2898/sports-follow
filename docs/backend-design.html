Sports Follow · backend

A player-first pipeline for live sports data

How the service finds sources for any athlete in any sport, keeps their live games, fixtures, stats and news fresh, and serves one shared record to every fan who follows them.

29 Sep 2026Draft for reviewCompanion to the app design canvas

Summary

The backend has two halves. A pipeline turns public sources into one canonical record per player: profile, live state, fixtures, results, season stats and news. A serving layer materializes that record as a player card and fans it out to everyone following the player, over a stream for live games and over a cacheable API for everything else.

Work is keyed by player and event, never by fanA fan following a player adds a subscription, nothing else. Ten thousand fans of Kohli cost the same to ingest as one.
Live polling is armed by the scheduleNothing is polled fast unless an event involving a followed player is about to start or in progress. Fixtures decide when the fast lane switches on.
Sources resolve themselves, then check their own healthA resolver maps a name to external ids and adapters; an LLM agent fills gaps; a health loop rediscovers sources that go stale.
1

Requirements and assumptions

Functional

  • Given a player name in any sport, identify the athlete and build their record: profile, teams, live game (score, clock, the player's own line), upcoming events, recent results, season and career stats, news.
  • Keep the record current: live state within seconds during a game, fixtures and stats within hours, news within minutes.
  • Serve the record to many fans at once, with a live stream during games and push notifications for the moments fans care about (game start, goal or wicket, milestone, big news).
  • Later: follow teams, compare two players. The data model should not have to change for either.

Non-functional

ConcernTargetWhy
Live freshness≤ 10 s behind the source; ≤ 2 s where the source pushesFans compare against TV and other apps. Slower than a minute feels broken.
Fixtures, results, stats≤ 1 hThey change a few times a day at most.
News≤ 5 minFeeds and news search are cheap to poll.
Read availabilityCards keep serving when the pipeline is down, stamped with their ageStale but honest beats an error page.
Scale (planning numbers)50k followed players · 1M follows · 100k fans online at a peakSizing in section 9. The design stays the same an order of magnitude either way.
CostNot a constraintWhat is constrained is the sources: most are free, unofficial and rate-limited, so resilience matters more than efficiency.

Constraints

  • Python. The research agent, the web tools and the report schema from the current app are reused as pipeline stages.
  • Every model call goes through the llm-providers gateway with the sports-follow app token, labelled per job.
  • Small team. Boring infrastructure by default: Postgres, Redis, a worker pool. Each choice below names what to swap in when it stops being enough.

3

Real-time updates per player

Very few sports sources push. Almost all of it is polling, so the question is what to poll and when. The answer is: poll events, not players, and let the schedule decide when an event is worth polling fast.

How it works

  1. Schedule ingest keeps an event row for every upcoming game of every team or tournament a followed player is in.
  2. A scheduler arms each event 30 minutes before its start: it enqueues a poll job with the event's live binding (a URL or stream endpoint from section 4) and a 60 s cadence.
  3. When a snapshot shows the event in progress, the cadence drops to the sport's live cadence. Each snapshot is stored raw (object storage, keyed by event and time), then normalized.
  4. When the source reports the event final, the poller takes one more snapshot and disarms. If the start passes with no in-progress signal for two hours, the event is marked postponed and returns to Scheduled.

Why one poll serves everyone

This is also why the app should show the game, with the followed players' lines inside it, rather than a separate feed per player. Kohli and Gill in the same ODI are one event state.

4

Finding sources for a player automatically

A source is only useful once it is bound to a specific player: an ESPNcricinfo id, a Lichess username, a FIDE id, a fixtures URL for their club. The resolver produces those bindings without a human, using structured id registries first and the LLM agent only where they run out.

Step by step

  1. Candidates. Query the Wikidata search API and a web search for the name. Wikidata gives a QID, occupation (sport), nationality and dates for each candidate. Most famous athletes resolve here without a model call.
  2. Disambiguate. If more than one candidate is an athlete, ask the model to pick the most likely one for a sports-follow app and to list the others. The others are stored on the player record so the app can show "did you mean".
  3. External ids. Wikidata holds ids for most source systems as properties: FIDE id (P1440), Transfermarkt id (P2446), ATP id (P536), ESPNcricinfo id (P2697), and many league and federation ids. Read every property the adapter registry knows.
  4. Adapters. Each adapter is code for one source system: how to turn an id into fixture, live, stats and news endpoints, how to parse them, and how to tell a live event from a finished one. An id plus an adapter is a binding.
  5. Gaps. When no adapter has an id (a domestic league, a new tournament, a niche sport), the discovery agent runs. It is the current research agent with a narrower job: return candidate URLs for fixtures, live scores, stats and news, each with evidence. The validator fetches every URL, confirms the page names the player and is recent, and only then writes a binding with the confidence and evidence attached.

Keeping sources fresh and finding new ones

Bindings rot. Pages move, ids change, a player transfers, a tournament site appears for one season. So every binding carries health, and health drives rediscovery.

TriggerWhat runsWhy
A fan follows a player nobody follows yetFull resolve and discovery, then schedule, stats and news ingest, with the fan's card marked "building"The first card should appear within a minute or two.
A binding fails 3 polls in a row, or returns a page that no longer names the playerMark it stale; try the next binding for the same purpose; queue rediscovery for that purpose onlyMost breakage is one endpoint, not the whole player.
No upcoming events are known for an active playerSchedule ingest across every binding, then discovery for a fixtures sourceAn empty "up next" usually means a missing source, not an idle player.
Weekly, per playerRe-resolve ids, refresh team membership, rerun discovery for purposes with low confidenceTransfers and squad changes show up here.
Season boundaries and new tournamentsA per-sport agent run that lists the season's competitions and proposes new adapters or bindingsNew competitions are the main way whole source families appear.

Two kinds of "new source"

  • A new binding for an existing adapter (a new tournament page on a known site) is found and verified automatically, as in section 4.
  • A new source system (a site the pipeline has never parsed) needs an adapter, which is code. The weekly per-sport agent run proposes them with sample URLs and a fetched example; an engineer approves and writes the adapter, or the system falls back to LLM extraction from the page (section 8) until one exists. Fallback bindings are flagged so their higher cost and latency are visible.

Health is scored per purpose (fixtures, live, stats, news), not per player, so a broken stats page never stops live scores. Every fetch keeps its raw response, which makes it possible to replay a day of snapshots through a fixed parser.

Canonical state is sport-specific inside, uniform outside

Every event has the same envelope (status, clock label, score label, as_of, source) so the app can render a card for any sport. The state and stats payloads follow one schema per sport, owned by that sport's adapters. This is the same shape as the report schema the current agent already returns; the pipeline fills it from structured sources instead of from a model.

{
  "event": "ind-wi-2026-odi-2",
  "status": "live",
  "score_label": "IND 214/3 (36.4 ov) v WI",
  "clock_label": "36.4 of 50 overs",
  "as_of": "2026-09-30T10:41:12Z",
  "source": "https://www.cricbuzz.com/live-cricket-scores/…",

Notifications

The card builder emits typed change events (event.started, line.milestone, event.final, news.new with its kind). A rules worker joins them with each follow's alert rules and hands the matches to the push provider. Teams later reuse the same events keyed by team.

Where the LLM sits

The model is never in the live hot path for a structured source. It does four jobs, each a gateway label so cost and latency show up per job in the gateway's telemetry.

Job (gateway label)WhenModel tierGuardrail
resolveAmbiguous names onlylargeOutput is a choice among fetched candidates, never a free-text fact.
discoverMissing binding, weekly sweeplarge, with web toolsEvery URL is fetched and checked before it becomes a binding.
extractLive or stats page with no adaptermediumSchema-constrained output; the extraction prompt is cached per page template, and a page that fails twice is flagged for an adapter.
newsEvery new itemsmallClassify kind and write a one-line summary; dedupe happens before the model, on URL and title similarity.
askA fan asks a question on a player pagelargeGrounded on the card and the stored history; this is the existing agent, reading from the store instead of the web.

Scale and reliability

Load, from the planning numbers

  • 50k followed players, of whom perhaps 5% have an event on at a busy hour: 2,500 live events. Players share events, so the count is closer to 1,000. At one poll every 8 s that is about 125 fetches per second across all sources, and a few per second per source host. A handful of poller workers.
  • 100k fans online, each holding one SSE connection: 10 to 20 API nodes, each subscribed once per distinct player its fans follow.
  • News at 50k players every 5 min is 170 feed fetches per second. Cheap, but it is the largest steady load, so it gets its own worker pool and per-host rate limits.

Failure modes and answers

FailureAnswer
A source blocks or rate-limits the pipelinePer-host token buckets, backoff, rotating user agents, and a second binding for every live purpose. Popular events are polled through more than one source and the freshest wins.
A source changes its page or JSON shapeAdapters have contract tests against stored snapshots; a parse failure marks the binding stale and switches to the next one, or to LLM extraction, while the alert goes to an engineer.
The pipeline is downCards keep serving from Redis and Postgres with their freshness stamps; the app shows "as of 14:02" rather than nothing.
Redis is lostCards are rebuilt from Postgres on demand; channels are recreated by the next publish. Nothing durable lives only in Redis.
Duplicate or wrong newsDedupe on canonical URL and title similarity before classification; items keep their source so a fan can judge them.
The resolver picks the wrong athleteThe card shows the disambiguation and a "not who you meant?" action that re-follows a listed alternative; the wrong record is not deleted, only unfollowed.

What to watch

  • Freshness per card, split by purpose: age of live state during live events is the headline metric.
  • Binding health: stale bindings per adapter, and the share of live purposes served by LLM extraction instead of an adapter.
  • Poll latency and error rate per source host; fan-out lag from snapshot to SSE delivery.
  • Gateway telemetry per label: calls, cost, duration, warnings. The gateway already records these.

Build order

  1. Registry and cards. Postgres schema, the card read model, GET card and follows. Fill cards with the existing agent's report so the app works end to end on day one, slowly.
  2. Adapters for two sports. Cricket (Cricbuzz, ESPNcricinfo) and football (ESPN), with schedule ingest and the event lifecycle. This replaces the agent for fixtures and live in those sports.
  3. Live fan-out. Redis card hash, per-player channels, the SSE endpoint, freshness stamps in the app.
  4. Resolver and discovery. Wikidata ids, the adapter registry, the discovery agent behind the validator, binding health.
  5. News and notifications. Feed ingest, dedupe, classification, alert rules, push.
  6. More sports, then teams. Chess (Lichess stream), tennis, F1. Team follows are subscriptions on team plus a team card built from the same events.

What to revisit as it grows: the job queue and pub/sub choice (section 10), typed stats for the compare feature, and whether the per-sport weekly agent sweep should become a standing catalog of competitions maintained by hand once the adapter set stabilizes.

Where the gaps are

  1. Cross-sport depth. A fan of Kohli, Carlsen and Alcaraz needs Cricbuzz, ChessEver and ATP WTA Live today. Generalists model players only where they hold a feed, which is why Flashscore covers 30 sports and follows players in two. The player line inside the game (section 3), applied uniformly, is the difference.
  2. The long tail. Incumbents stop where their data contracts stop: domestic leagues, niche sports, retired athletes. The resolver and discovery agent (section 4) are the only approach in the table that can cover a player nobody has a feed for.
  3. AI that follows rather than answers. The AI entrants are chat boxes over a publisher's data. Nobody combines persistent following, live state and a grounded question-answering agent on the same record; that is the ask job in section 8.
  4. Alert quality. The recurring complaint in reviews and industry pieces is notification noise. Per-player alert rules are table stakes (theScore, FotMob, Cricbuzz all have them). Classifying news so that "big news only" means that is not, and the pipeline already does the classification step.
